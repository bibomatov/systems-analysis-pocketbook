Системный анализ:
карманный справочник

Документ описывает принципы построения, редакционные требования и техническую структуру справочника по системному анализу. Служит ориентиром для авторов, редакторов и разработчиков, которые поддерживают и развивают книгу.

Краткое содержание для соавтора

Если читаете документ впервые, начните с этого блока. Подробности — в основном тексте.

  1. Миссия — единый открытый русскоязычный справочник по системному анализу для развития профессии в России. Бесплатно. Подробнее: § 00.
  2. Три читателя: Junior, Middle, Senior-специалист в узкой области. Каждая тема устроена так, чтобы все трое вышли на одинаковый уровень понимания. Подробнее: § 01.
  3. Главный принцип — выравнивание уровня понимания. Объём темы определяется требованием понимания, не лимитом слов. Производный принцип — порядок: сначала определение и ментальная модель.
  4. Принцип материальности — абстрактные концепции обязательно привязываются к материальной форме. «WSDL — это XML-файл, который сервер отдаёт по URL ?wsdl». Подробнее: § 02.
  5. Стиль — профессиональный без академической сухости и без разговорной фамильярности. Минимум англицизмов. Источники в «Дополнительных источниках» — только русскоязычные.
  6. Структура — 19 глав в 8 частях. Три шаблона темы: полный, средний, краткий. В составных главах темы группируются в подразделы. Подробнее: § 03, § 04.
  7. Ревью — каждая глава ревьюится тремя ролями: senior-аналитик (контент), литературный редактор (стиль), senior-верстальщик (техника, после части целиком). При несогласии AI-ревьюера и автора — приоритет за автором. Подробнее: § 10.
  8. Технически — отдельный HTML-файл на главу, общая дизайн-система в styles.css, сборка скриптом build.py. Рабочие документы — в meta/, автосборка и публикация на GitHub Pages — через Actions. Подробнее: § 12.
§ 00

Проблема и миссия

Книга закрывает определённый пробел в профессиональной литературе и служит развитию сообщества. Любое содержательное решение проверяется по этой секции.

Проблема

В русскоязычном пространстве нет единого открытого источника по системному анализу. Существующие материалы делятся на три категории, и ни одна не закрывает потребность практикующего специалиста:

  • Академические учебники — оторваны от практики. Дают теоретическую базу, но язык изложения мешает её применить.
  • Разрозненные статьи и видео — поверхностны и противоречат друг другу. Найти ответ можно, целостную картину собрать — нет.
  • Платные курсы — закрыты для значительной части специалистов. Особенно болезненно это для начинающих, у которых нет ни знаний, ни денег на их покупку.

Профессия в стране развивается медленнее, чем могла бы. Барьер для входа новых людей высокий. Каждое поколение аналитиков собирает знания заново — из разрозненных источников и личной практики.

Миссия

Главная цель

Создать единый открытый русскоязычный справочник по системному анализу, доступный безвозмездно. Помочь начинающим войти в профессию, действующим — структурировать и расширить знания, опытным — поддерживать актуальность на смежных темах. Развитие системного анализа в России — главная цель книги.

Проверочный критерий

Любое содержательное решение проверяется одним вопросом: «Помогает ли это русскоязычному специалисту в реальной работе или обучении?». Если ответ нет — решение пересматривается, даже если оно красиво в теории.

§ 01

Введение

Это справочник, а не учебник. Он не ведёт читателя через предметную область, а даёт точные ответы на точечные вопросы. Здесь — для кого книга, как её читать и на каких принципах построена.

Что это за книга

Справочник по системному анализу в карманном формате. Покрывает ключевые темы предметной области: процессы и роли, требования, моделирование, базы данных и SQL, интеграции, архитектуру, безопасность, пользовательский интерфейс. Глубина каждой темы — достаточная для понимания и применения, без ухода в нишевую специфику.

Формат вдохновлён карманными справочниками O'Reilly Pocket Reference: компактные, точные, оптимизированные под повторное обращение, а не одноразовое чтение. Цель — дать читателю инструмент, к которому он будет возвращаться в работе на протяжении лет.

Для кого книга

Книга адресована трём типам читателей одновременно. Структура каждой темы устроена так, чтобы все трое находили нужное:

Junior-аналитик

Начинающий специалист: студент, выпускник переквалификации, аналитик с опытом до года. Уже владеет базой: понимает, как работает HTTP на уровне «запрос — ответ», умеет читать простой SQL SELECT, имеет представление о клиент-серверной модели. Но многие концепции системного анализа ему незнакомы, а часть знакомых — поверхностна.

Цель чтения — освоить базовые концепции и выйти на единый уровень понимания с действующими специалистами. Ключевое требование к подаче — возможность «пощупать руками». Абстрактное объяснение без привязки к материальной форме у этого читателя не закрепляется. Если тема описывает WSDL, недостаточно сказать «контракт веб-сервиса» — нужно добавить, что это XML-файл, который сервер отдаёт по URL и который можно открыть в браузере.

Middle-аналитик

Действующий специалист с опытом 1–5 лет. Владеет основными темами на уровне применения. Использует книгу для быстрого освежения перед задачей, встречей или согласованием. Дополнительный сценарий — подготовка к собеседованиям: нужно структурированное знание системного анализа, охватывающее всю предметную область равномерно.

Senior-специалист в узкой области

Опытный аналитик, который долго работал на одном проекте или в одном стеке. В своей области владеет и теорией, и практикой. Сложность — выйти на смежные темы: давно не было альтернативных контекстов. Может, например, забыть базовые механики HTTP-заголовков, если в его стеке последние годы использовался только gRPC. Книга для него — способ восстановить картину профессии в полном объёме.

Как пользоваться

Книга не предполагает линейного чтения, хотя оно возможно. Основной режим — точечное обращение через оглавление или поиск. Каждая тема устроена так, что её можно читать в отрыве от соседних:

  • Junior читает тему сверху вниз, обращает внимание на определение, ментальную модель и пример. Блоки «когда применять» и «чеклист» может пропускать — они для практики, которая придёт позже.
  • Middle прыгает к чеклисту и блоку типичных ошибок, по необходимости возвращается к ментальной модели.
  • Senior читает определение и ментальную модель, использует таблицы сравнения как опорную точку.

На каждую главу даётся блок «что вы узнаете». В конце главы — короткое резюме и список дополнительных источников.

Главный принцип: выравнивание уровня понимания

Принцип

Приоритет книги — объяснение темы, а не краткий ответ на вопрос. Задача — чтобы читатели всех трёх уровней пришли к одинаковому уровню понимания темы. Тема считается завершённой, когда любой из трёх целевых читателей может объяснить её своими словами после одного прочтения.

Из этого следует, что объём темы определяется требованием понимания, а не количеством слов. Если для выравнивания нужно больше слов — пишем больше; если меньше — меньше. Лимиты в § 02 — ориентиры, а не нормативы.

Производный принцип: порядок изложения

Главный принцип определяет что даёт тема. Этот принцип определяет, в каком порядке подавать материал.

Каждая тема начинается с определения и ментальной модели. Уже первый блок должен дать читателю основу для самостоятельного продолжения, даже если он закроет страницу. Дальше идут детали: как устроено, пример, нюансы. Исторические справки и контекст — в конце или в заметках на полях.

Это правило про последовательность, а не про объём. Главный принцип требует полного объяснения; этот — требует, чтобы оно начиналось с самого важного.

Условные обозначения

В тексте встречаются повторяющиеся визуальные блоки. Их семантика фиксирована и единообразна по всей книге:

§ 02

Редакционный стандарт

Правила, по которым пишется содержание книги. Их цель — единообразие стиля независимо от того, кто пишет конкретную тему, и предсказуемость опыта чтения для пользователя.

Тон и подача

Профессиональный, без академической сухости и без разговорной фамильярности. Тон справочника, к которому читатель возвращается за конкретным ответом, а не статьи в блоге.

Делаем так
  • Полные предложения, читается линейно
  • Объясняем «зачем» до «как»
  • Один абзац — одна мысль
  • Конкретное называние явлений, а не намёки на них
  • Безличные конструкции или нейтральное второе лицо («обратите внимание»)
Так не делаем
  • Разговорные обороты: «давайте попробуем», «как мы видим», «грубо говоря»
  • Эмоциональные оценки: «отличный подход», «ужасно неудобно»
  • Академический канцелярит: «является», «осуществляется», «представляет собой»
  • Телеграфные тезисы без связок
  • Длинные риторические вступления и переходы

Лексика и термины

Минимизация англицизмов там, где есть устоявшиеся русские эквиваленты. Технические термины-названия (API, REST, HTTP, SQL, Kafka, JWT, JOIN и подобные) остаются на английском — это имена собственные, а не калька.

Правило

При первом упоминании русского термина — английский в скобках: «хранимая процедура (stored procedure)». При первом упоминании аббревиатуры — расшифровка: «REST (Representational State Transfer)». Дальше по тексту — без повторного раскрытия.

Структура текста

  • Предложения короткие. Длинные сложноподчинённые конструкции — только когда без них теряется смысл.
  • Один абзац — одна мысль. Объём абзаца — 3–6 предложений. Если разрастается до 8+ — сигнал к разбиению.
  • Без водянистых вводных. «В современном мире», «как известно», «давно не секрет», «стоит отметить» — удаляются.
  • Без избыточных квалификаторов. «Достаточно часто», «можно сказать», «в некотором роде» — конкретизируются или удаляются.

Объём темы

Объём определяется требованием понимания, а не количеством слов. Цель — чтобы читатель любого из трёх целевых уровней мог объяснить тему своими словами после её прочтения. Если для этого нужно больше — пишем больше; если меньше — меньше.

Ниже приведены ориентиры по объёму для трёх шаблонов. Это не нормативы, а указатели направления — если тема выходит сильно за рамки, имеет смысл проверить, не разрастается ли она в сторону отдельной главы или, наоборот, не пропущена ли часть объяснения.

Принцип материальности

При объяснении абстрактных концепций обязательна привязка к материальной форме: где это лежит, как это выглядит, что с этим можно сделать руками. Для junior-аналитика без такой привязки абстрактное знание не закрепляется.

Делаем так

WSDL — это XML-файл, описывающий контракт SOAP-сервиса. Сервер отдаёт его по URL (обычно с суффиксом ?wsdl в конце адреса). Файл можно открыть в браузере, сохранить локально, передать в генератор клиентского кода — он создаст из WSDL заготовку для вызова сервиса.

Так не делаем

WSDL — это контракт веб-сервиса, описывающий его интерфейс. Используется в SOAP-протоколе для формализации взаимодействия между клиентом и сервером.

Сторонние темы внутри объяснения

Когда тема ссылается на другое понятие, читатель не должен останавливаться и идти искать. Дайте короткое напоминание прямо в тексте — одно-два предложения — и ссылку на основную тему для тех, кому нужно больше.

Пример

«При вызове защищённого API клиент передаёт токен в HTTP-заголовке Authorization (заголовки HTTP — это пары ключ-значение в начале запроса, см. главу 10). Сервер извлекает токен из заголовка и проверяет его подпись...»

Правило

Напоминание о сторонней теме — максимум одно-два предложения. Если требуется больше — это сигнал, что плохо выбран порядок глав, тема перегружена, или нужно вынести объяснение в глоссарий.

Примеры

  • Конкретные, не абстрактные. Не «система X», а «интернет-магазин», «сервис заказов», «платформа подписок».
  • Универсальный бизнес-контекст. Электронная коммерция, заказы, пользовательские профили — нейтральные, понятные любому. Банковская и другая отраслевая специфика — только когда она объясняет тему лучше других (например, идемпотентность платежей).
  • Реалистичные цифры. «100 RPS», «24 часа», «50 МБ» — не «много», «быстро», «большой».
  • Один пример — одна идея. Если пример иллюстрирует несколько концепций сразу, читатель путается.

Заголовки тем

В виде существительного-фрагмента — это формат справочника, а не Q&A. Заголовок именует тему, а не задаёт вопрос или утверждение.

Делаем так
  • «Идемпотентность HTTP-методов»
  • «Нормализация и денормализация»
  • «Оркестрация и хореография»
  • «Свойства транзакций ACID»
Так не делаем
  • «Что такое идемпотентность?» — Q&A-формат, не справочник
  • «Идемпотентность важна» — пустое утверждение
  • «Поговорим про SAGA» — разговорный тон
  • «Всё о CAP-теореме» — обещание, которое нельзя выполнить

Чего избегать

  • Слов-паразитов: «просто», «очевидно», «легко», «понятно», «как мы видим». То, что очевидно одному, может быть непонятно другому — формулируем без оценок сложности.
  • Эмоциональных усилителей: «крайне важно», «абсолютно необходимо», «совершенно недопустимо». Если что-то важно, объясняем причину, а не усиливаем словами.
  • Заглавных букв для эмфазиса: «НИКОГДА не делайте Х». Для выделения есть <strong> и семантические блоки.
  • Эмодзи в основном тексте. Семантику передают цвет и форма карточек.
  • Сокращений из чата: имхо, кстати, имеется ввиду, ну и т.д.
  • Авторских вкраплений: «по моему опыту», «когда я работал в…». Книга безличная.
§ 03

Каркас оглавления

Восемь частей, девятнадцать глав. Сложные главы делятся на подразделы — это позволяет дать каждой нотации, протоколу или концепции достаточно места без дробления оглавления на 30+ глав.

Четырёхуровневая иерархия

Книга строится по четырём уровням: часть → глава → подраздел → тема. Подразделы вводятся только в составных главах, где нужно раскрыть несколько крупных смысловых блоков. В простых главах четвёртого уровня нет — там сразу часть, глава, темы.

Каждая запись в подразделе ниже — это отдельная тема, написанная по одному из трёх шаблонов (§ 04). Подраздел — это группировка тем, не самостоятельная единица содержания.

Порядок и логика

Порядок — от мышления к технике. Сначала — суть системного анализа как деятельности, его роль и место в проекте. Затем — главная активность аналитика (работа с требованиями) и инструменты формализации. Дальше — предметные области по порядку приближения к коду: данные, интеграции, архитектура, безопасность, интерфейс.

§ 04

Структура темы и главы

Книга состоит из глав, главы — из тем. В составных главах между уровнем главы и уровнем темы добавляется промежуточный уровень — подраздел. Каждая тема имеет внутреннюю структуру по одному из трёх шаблонов.

Структура главы

Каждая глава имеет одинаковый каркас, который облегчает навигацию и повторное обращение:

Обёртка главы единый каркас для всех 19 глав
  1. Заголовок и подзаголовок — название главы и одно-двухпредложное описание области, которую она покрывает
  2. Что вы узнаете — 4–6 буллетов о том, что читатель освоит после главы. Позволяет решить, нужна ли глава прямо сейчас
  3. Карта главы (опционально, только для составных глав с 5+ темами) — короткая визуальная или текстовая схема связей между темами главы. Помогает читателю не потеряться в большом материале
  4. Темы главы — последовательность тем по выбранным шаблонам. В составных главах темы сгруппированы в подразделы
  5. Резюме — 3–5 ключевых тезисов главы для повторного обращения
  6. Дополнительные источники — русскоязычные книги, статьи, RFC по теме главы, со ссылками на материалы автора при наличии

Подразделы (в составных главах)

Если глава раскрывает несколько крупных смысловых блоков, между уровнем главы и уровнем темы вводится промежуточный уровень — подраздел. Это позволяет дать каждому блоку достаточно места без дробления оглавления.

Примеры составных глав: «Нефункциональные требования» (производительность, масштабируемость, надёжность и т.д.), «Нотации моделирования» (UML, BPMN, C4, DFD, ER), «Базы данных» (реляционные, NoSQL, ACID/BASE), «SQL» (DDL, DML, запросы, индексы, транзакции), «Асинхронные интеграции» (концепции, RabbitMQ, Kafka), «Архитектурные стили» (монолит, SOA, микросервисы, EDA, моделирование событий), «Распределённые системы» (CAP, репликация, шардирование, кэш, балансировка, API Gateway, SAGA), «Безопасность» (Identity, AuthN, AuthZ, OAuth/JWT, шифрование, защита данных, OWASP).

Структура подраздела
  1. Заголовок подраздела — название блока без избыточных пояснений
  2. Краткое введение — одно-два предложения о том, что покрывает подраздел
  3. Темы подраздела — последовательность тем по выбранным шаблонам

Резюме и источники остаются на уровне главы целиком — не дублируются для каждого подраздела.

Опциональные блоки темы

В дополнение к базовым блокам шаблона тема может содержать максимум один опциональный блок из закрытого списка. Опциональные блоки нужны только тогда, когда без них тема будет неполной — не для красоты.

БлокКогда применяется
Историческая справкаКогда без эволюции тему не понять: «было так → стало эдак → почему сменилось». Например, у OAuth, методологий разработки
Обоснование / доказательствоКогда утверждение неочевидно и требует упрощённого объяснения. Например, CAP-теорема, выбор между шаблонами доставки сообщений
Эволюция и устареваниеКогда тема имеет официальный или фактический статус: «устаревает», «заменяется на X». Например, SOAP, синхронные интеграции на больших нагрузках

Опциональный блок размещается после «Как устроено» и перед «Примером». Открывается заголовком уровня h3 в полном шаблоне (или h4 в среднем).

Правило

Микро-темы часто естественно собираются в общую таблицу сравнения внутри большой темы, а не в отдельные блоки. Например, в главе SQL все «X vs Y» лучше дать одной таблицей, чем серией маленьких карточек.

Принцип построения главы

Темы внутри главы упорядочены по принципу нарастающей сложности: фундаментальные концепции идут раньше прикладных. Это позволяет junior-аналитику читать главу линейно, а более опытному читателю — пропускать первые темы и сразу идти к тому, что ему нужно.

§ 05

Визуальные компоненты

Одиннадцать компонентов, которые повторяются на протяжении всего файла. Все они уже использованы в этом документе — это не просто описание, а живая демонстрация.

1. Карточка определения

Определение

Идемпотентность — свойство операции, при котором её повторное выполнение с теми же параметрами даёт тот же результат, что и одно выполнение. Не путать со «свойством возвращать одинаковый ответ» — речь о побочных эффектах.

2. Блок «делай / не делай»

Двухколоночный, для прямого сопоставления хороших и плохих практик. Пример выше в разделе «Стиль и тон».

3. Блок предупреждения / нюанса

Важно

Идемпотентность PUT — это требование стандарта HTTP, а не свойство, которое появляется само. Если ваш PUT при втором вызове ведёт себя иначе — это баг реализации, а не особенность HTTP.

4. Блок антипаттерна

Антипаттерн

Делать POST /orders идемпотентным «по содержимому» — проверять, есть ли уже заказ с такими же позициями, и не создавать дубль. Это ломается при легитимных повторных заказах того же товара и не решает реальную задачу защиты от ретраев.

7. Чеклист

  • В POST-операциях, создающих ресурсы с побочными эффектами, поддерживается Idempotency-Key
  • Ключ хранится не меньше окна возможных ретраев (обычно 24 часа)
  • На дублирующий запрос возвращается тот же ответ, а не новая операция
  • Документация явно описывает, какие операции идемпотентны
  • В тестах проверяются повторные вызовы — не только «happy path»

12. Заметка на полях (margin note)

Дополнительный компонент для финального справочника. На широких экранах выносится в правое поле страницы рядом с соответствующим абзацем; на узких — становится inline-сноской ниже абзаца. Используется для коротких уточнений, цитат из книг и связанных идей, которые не должны прерывать основной текст.

Идемпотентность в HTTP — это контракт, а не свойство протокола. RFC 7231 определяет, какие методы обязаны быть идемпотентными, но если ваш сервер реализован неправильно, повторный PUT может создать дубль или поменять состояние неожиданно.

На полях

«Если требование нельзя протестировать — это не требование, а пожелание». — Вигерс. Тестируйте идемпотентность повторными вызовами.

§ 07

SVG, навигация, ссылки

Технические правила: где ставим схемы, как работает оглавление, как устроены связи между темами.

SVG-схемы

Все схемы встраиваются inline в HTML, не как внешние файлы. Финальный документ остаётся самодостаточным — один HTML без папки картинок.

В репозитории есть готовый запас из 34 SVG в папке assets/svg/ — это исходники из базы знаний автора по большинству ключевых тем (JOIN, SAGA, OAuth flow, SDLC, BPMN, C4 и др.). Они служат стартовой точкой для иллюстраций в книге.

Алгоритм работы автора темы
  1. Перед созданием SVG проверить assets/svg/ — есть ли подходящая схема по теме
  2. Если есть — использовать как стартовую точку. Адаптировать под дизайн-систему книги: заменить захардкоженные цвета на CSS-переменные, шрифт Arial на IBM Plex Sans (или убрать font-family для наследования)
  3. Если нет — создать новую SVG в едином стиле дизайн-системы. Сохранить исходник в assets/svg/
  4. В финальный HTML главы SVG встраивается inline, а файл в assets/svg/ остаётся как версионируемый исходник
Когда схема обязательна
  • Структурные отношения между компонентами (C4, Kafka, архитектурные стили)
  • Процессы во времени (OAuth flow, SAGA, sequence-диаграммы)
  • Сравнения с пространственной составляющей (JOIN, партиционирование)
  • Концептуальные модели, которые легко спутать (queue vs topic, polling vs webhook)

Навигация финального справочника

Финальный документ — двухуровневый: 19 глав, в каждой 3–11 тем. Поэтому две колонки навигации работают на разных уровнях иерархии:

  • Левая колонка (глобальная навигация) — оглавление всех 19 глав документа, всегда видимая, подсвечивает текущую главу.
  • Правая колонка (локальная навигация) — темы внутри текущей открытой главы, появляется на широких экранах от 1500px. Например, при чтении главы «SQL» справа будет «Типы JOIN, UNION, оптимизация запросов, оконные функции...».
Правило

Две колонки навигации применяются только там, где они работают на разных уровнях иерархии. В одноуровневых документах (как эта концепция) правая колонка не нужна — она будет дублировать левую.

Прочие элементы

  • Якоря на каждую главу и тему — для прямых ссылок
  • Кросс-ссылки между темами — рабочие <a href="#anchor"> в блоках связей
  • Кнопка «наверх» — фиксированная справа внизу (добавим в финальном файле)
  • Поиск — нативный Ctrl+F браузера, без кастомных решений
§ 08

Глоссарий

Алфавитный указатель ключевых терминов с короткими определениями и ссылками на основные главы. Самостоятельный артефакт, отдельный от глав.

Назначение

Глоссарий — точка входа для junior-аналитика, который встретил незнакомый термин и хочет получить определение в одну строку, а не читать целую главу. Для middle и опытного читателя — справочное приложение для быстрой проверки.

Структура записи

Каждая запись содержит четыре элемента: термин, краткое определение в одно-два предложения, английский эквивалент в скобках, ссылку на основную главу. У каждой записи есть якорь вида gloss-{slug} — для прямых ссылок из глав.

<article id="gloss-idempotency"> Идемпотентность (idempotency) Свойство операции, при котором повторное выполнение с теми же параметрами даёт тот же результат. → Глава 15. Сквозные темы интеграций </article>

Правила составления

  • Один термин — одна запись. Не объединяем близкие термины в одну запись, даже если они часто упоминаются вместе.
  • Определение в глоссарии ≠ определение в главе. В глоссарии — самое сжатое, в главе — развёрнутое.
  • Алфавитный порядок русского названия. При англицизмах (REST, JWT) — по русской транскрипции или по латинской букве в начале латинского блока.
  • Без перекрёстных определений. Если в определении одного термина встречается другой термин из глоссария, на него стоит ссылка, но не повторяется его определение.

Обогащение глоссария при написании главы

Правило

Каждая написанная тема обязательно добавляет в глоссарий минимум один термин — обычно тот, который сформулирован в блоке «Определение». Глоссарий собирается не итоговой задачей в конце книги, а растёт параллельно с написанием глав. Без этого правила глоссарий не появится никогда.

Размещение и якоря

Файл glossary.html в корне репозитория. В оглавлении книги — отдельная позиция после всех глав. Якорь каждой записи имеет формат gloss-{slug}, где slug — короткое английское обозначение термина латиницей, через дефис, без подчёркиваний и заглавных букв (например, gloss-idempotency, gloss-saga, gloss-cap-theorem). Кросс-ссылки из глав используют этот якорь: <a href="../glossary.html#gloss-idempotency">идемпотентность</a>.

§ 09

Источники и цитаты

Книга опирается на профессиональную литературу, отраслевые стандарты и документацию. Правила использования источников едины по всей книге — это нужно для доверия читателя и проверяемости утверждений.

Принцип русскоязычности

Принцип

Все источники в разделе «Дополнительные источники» — на русском языке. Это книги, статьи, RFC с русским переводом, отраслевая документация. Иноязычные источники ссылками не указываются, чтобы у читателя был прямой доступ к материалу без языкового барьера.

Это требование вытекает из миссии книги: помочь русскоязычным специалистам, у которых нет доступа к платным курсам и нет привычки читать английскую литературу. Если все ссылки уведут в англоязычные источники, книга потеряет половину своей пользы.

Цитаты из иноязычных авторов

Цитаты-принципы могут происходить из любых источников, включая англоязычные. В этом случае действует правило:

  • Цитата приводится в русском переводе
  • В подписи указывается автор и оригинальное название работы
  • Если перевод книги существует на русском — даётся ссылка на русское издание в источниках главы
  • Если перевода нет — цитата всё равно используется, но в источниках не упоминается
Пример
Если требование нельзя протестировать — это не требование, а пожелание. Карл Вигерс, «Разработка требований к программному обеспечению»

Приоритет источников

При выборе источников для главы соблюдается следующий приоритет:

  1. Конспекты автора по 16 ключевым книгам — стартовый ориентир для тем, которые в этих книгах раскрыты
  2. Русскоязычные книги и переводы — Вигерс, Орлов, Голощапов, Клеппман в переводе, классические российские учебники по системному анализу
  3. Русскоязычные отраслевые материалы — статьи на Habr, материалы конференций (Yandex Scale, Highload++, СберТех, T-Bank.tech), документация компаний на русском
  4. Стандарты и RFC — ГОСТы, IEEE, ISO/IEC, IETF — со ссылкой на русский перевод при наличии

Что не используется

  • Личные блоги без рецензирования или верификации содержания
  • Ответы StackOverflow и подобных платформ как первоисточник (можно использовать для перепроверки, но не для ссылки)
  • Видео без сопровождающей текстовой статьи — не подходит как источник для книжного формата
  • Платные ресурсы за пейволом — противоречит миссии книги
§ 10

Процесс ревью

Каждая глава и книга целиком проходят ревью через три специализированные роли. Это не заменяет личное ревью автора, но даёт системный взгляд с трёх разных профессиональных позиций.

Принцип ролевого ревью

Ревью проводится от лица персон, каждая из которых смотрит на материал через свой профессиональный фильтр. Персоны не имеют контекста процесса написания — оценивают материал «с нуля», как если бы открыли готовую главу впервые. Это даёт честную обратную связь, не искажённую знанием авторских намерений.

Оговорка

Ролевое ревью имеет ограничения: AI имитирует роли на основе обученных данных, а не обладает реальным десятилетним опытом. Поэтому ревью от персон дополняет, а не заменяет личное ревью автора и привлечение реальных специалистов. AI-ревьюер обязан честно отмечать места, где он не уверен.

Три роли

Senior+ системный аналитик Контент

Десять лет опыта работы в крупных российских IT-компаниях, активная практика обучения стажёров и младших коллег. Оценивает:

  • Корректность фактов и точность определений
  • Актуальность подходов — соответствие современной отраслевой практике
  • Глубину объяснения — достаточно ли для понимания, не избыточно ли
  • Стиль изложения с точки зрения профессионального читателя
  • Покрытие темы — что важного упущено
Литературный редактор Стиль и структура

Опыт редактирования технической литературы в бумажном и электронном виде. Оценивает:

  • Стиль изложения: соответствие редакционному стандарту
  • Структуру текста: логику переходов, связность абзацев
  • Визуальную часть содержания: уместность блоков, таблиц, схем
  • Чистоту языка: канцелярит, англицизмы, слова-паразиты
  • Единообразие терминологии в рамках главы и книги в целом
Senior+ верстальщик Техническая часть

Опыт работы с большими разнородными проектами в HTML/CSS. Оценивает не содержание, а техническое исполнение:

  • Организацию репозитория — масштабируемость, удобство расширения
  • Качество вёрстки — оптимальность с учётом будущих частых изменений
  • Чистоту HTML и CSS, использование общих стилей
  • Семантическую корректность разметки
  • Производительность и поведение на разных экранах

Когда применяется каждая роль

ЭтапКонтентСтильТехника

После написания каждой главыОбязательноОбязательно—
После каждой части (2–4 главы)——Обязательно

Формат ревью

Каждое ревью оформляется по единой структуре, чтобы автор мог быстро понять приоритет правок:

  1. Сильные стороны — что сделано хорошо, что сохранить
  2. Критические замечания — что обязательно исправить перед фиксацией
  3. Существенные замечания — что стоит улучшить, но не блокирует
  4. Рекомендации — что можно улучшить, на усмотрение автора
  5. Места неуверенности AI — где AI-ревьюер не может дать надёжную оценку и нужен реальный специалист

Разрешение конфликтов с AI-ревьюером

Правило

При несогласии AI-ревьюера и автора приоритет за автором. AI-ревьюер должен явно отмечать спорные места как требующие проверки реальным специалистом. Автор имеет право отклонить замечание AI с короткой пометкой «проверено в своей практике» — этого достаточно, дополнительное обоснование не требуется.

Это правило существует, чтобы AI-ревью не превращалось в диктат. AI имитирует роли на основе обученных данных; реальный опыт автора в живой профессии — выше по приоритету.

§ 11

Алгоритм работы над главой

Унифицированная последовательность шагов для каждой новой главы. Применяется независимо от того, кто пишет — автор лично или с AI-ассистентом, в одной сессии или в нескольких.

Последовательность шагов

  1. Анализ исходных материалов. Просмотр имеющихся источников по теме главы: конспекты книг, существующие материалы автора, отраслевая документация. Формирование чернового списка тем и подразделов.
  2. Согласование разбивки. Утверждение списка тем, подразделов (если применимо), выбор шаблона для каждой темы (полный, средний, краткий). На этом шаге фиксируется структура главы.
  3. Написание пилотной темы. Сначала пишется одна тема как образец — лучше из середины списка, не самая лёгкая и не самая сложная. Цель — установить рабочий ритм и проверить, что выбранный шаблон работает для главы.
  4. Ревью пилотной темы. Применение ролей «Senior+ аналитик» и «Литературный редактор». Корректировка подхода при необходимости.
  5. Написание остальных тем. После одобрения пилотной темы — массовое написание остальных тем по тому же ритму. Темы пишутся в порядке оглавления главы.
  6. Сборка главы. Дополнение обёртки главы: «Что вы узнаете», резюме, дополнительные источники. Проверка кросс-ссылок внутри главы.
  7. Ревью главы целиком. Полный проход двух персон по собранной главе. Корректировка по результатам.
  8. Обновление кросс-ссылок в соседних главах. Если новая глава делает доступными ссылки, которые ранее ссылались в пустоту — обновление навигации в смежных главах.
  9. Коммит и пересборка книги. Финальная фиксация главы в репозитории, пересборка pocket-book.html.

Принцип «один чат — одна глава»

При работе с AI-ассистентом каждая глава пишется в отдельном чате внутри проекта. Это предотвращает раздувание контекста и обеспечивает чистоту работы. Между чатами контекст передаётся через файлы проекта, в первую очередь через этот документ.

Информирование о смене настроек

Обязательное правило для AI-ассистента

AI обязан проактивно сообщать пользователю о необходимости сменить модель или включить/выключить расширенное размышление перед началом задачи, для которой это критично. Не предполагать, что пользователь сам помнит. Формулировка должна быть конкретной: «Перед следующим сообщением переключи на Opus и включи расширенное размышление — это будет ревью сложной темы».

§ 12

Структура репозитория и сборка

Документ хранится разбитым на файлы — это нужно для удобства Git, чистых diff'ов и предсказуемых правок. Финальная версия для чтения собирается в один HTML и публикуется автоматически на GitHub Pages.

Структура файлов

pocket-book-sa/ ├── styles.css # единая дизайн-система ├── index.html # главная: hero, миссия, оглавление (эталон TOC) ├── chapters/ │ ├── 00-intro.html # введение │ ├── 01-role.html # одна глава = один файл │ ├── 02-sdlc.html │ ├── 03-requirements-types.html │ └── ... # всего 19 глав + введение ├── meta/ # документы о книге, не часть книги │ ├── editorial-standard.html # этот документ │ └── project-instructions.md # инструкции для AI-ассистента ├── assets/svg/ # SVG-исходники: 34 готовых + новые при написании глав ├── .github/workflows/ │ └── build-and-deploy.yml # автосборка и публикация на Pages ├── build.py # скрипт сборки и валидации ├── pocket-book.html # финальный собранный файл (в .gitignore) ├── glossary.html # глоссарий, растёт параллельно с главами ├── README.md ├── CONTRIBUTING.md ├── LICENSE # CC BY 4.0 └── .gitignore

Разделение «книга» и «документы о книге»

Файлы книги (index.html, chapters/*.html, glossary.html, styles.css) попадают в собранный pocket-book.html и публикуются как корневой сайт. Файлы в meta/ — рабочие документы для авторов и редакторов: они не входят в собранную книгу, но публикуются отдельно на Pages по адресу /meta/.

Маркеры в файлах

Сборка и синхронизация работают по служебным маркерам-комментариям. Они не удаляются и не переименовываются — на них ориентируется build.py:

МаркерГде живётНазначение
<!-- INDEX-CONTENT-START --> / ENDindex.htmlГраницы основного контента главной — попадает в pocket-book.html перед главами
<!-- CHAPTER-CONTENT-START --> / ENDchapters/*.htmlГраницы контента главы — то, что извлекается при сборке
<!-- TOC-GLOBAL-INCLUDE --> / /...index.html, все главыГлобальное оглавление — один источник правды в index.html, синхронизируется во все главы
<!-- TOC-LOCAL-INCLUDE --> / /...chapters/*.htmlЛокальное оглавление главы — темы текущей главы для правой колонки

Соглашение по ID и якорям

Чтобы избежать конфликтов идентификаторов между главами при росте книги:

СущностьФорматПример
Файл главыchapters/NN-slug.htmlchapters/04-functional-requirements.html
ID главы (article)ch-NNid="ch-04"
ID темы (section)ch{NN}-{slug}id="ch04-user-stories"
ID подразделаch{NN}-sub-{slug}id="ch04-sub-formalization"
ID статьи глоссарияgloss-{term}id="gloss-idempotency"

Slug — короткое английское обозначение латиницей, через дефис, без пробелов, подчёркиваний и заглавных букв. ID главы (ch-NN) проставляется автоматически скриптом сборки при создании pocket-book.html.

Скрипт сборки

python3 build.py # собрать pocket-book.html python3 build.py --check # проверить HTML на баланс тегов и маркеры python3 build.py --sync-toc # синхронизировать глобальный TOC во всех главах

Скрипт работает на Python 3.10+ без сторонних зависимостей. Логика сборки: читает styles.css, извлекает контент из index.html (по маркерам INDEX-CONTENT) и из chapters/*.html (по маркерам CHAPTER-CONTENT), проставляет якоря id="ch-NN", преобразует кросс-ссылки на файлы глав в якорные, собирает один HTML со стилями inline и пишет в pocket-book.html.

Правило

Глобальный TOC — один источник правды в index.html. При добавлении, переименовании или изменении порядка глав правится только index.html, затем запускается python3 build.py --sync-toc. Скрипт обновит блок TOC-GLOBAL-INCLUDE во всех файлах chapters/*.html и адаптирует ссылки (уберёт префикс chapters/, поставит class="is-current" на текущую главу).

Автосборка через GitHub Actions

При каждом push в main запускается workflow .github/workflows/build-and-deploy.yml:

  1. python3 build.py --check — валидация HTML
  2. Проверка, что TOC во всех главах синхронизирован с index.html
  3. python3 build.py — сборка pocket-book.html
  4. Подготовка артефактов: книга кладётся в корень _site/ как index.html, документы из meta/ — в _site/meta/
  5. Деплой на GitHub Pages

После настройки Pages (Settings → Pages → Source: GitHub Actions) книга доступна по адресу https://<username>.github.io/<repo>/, редстандарт — по https://<username>.github.io/<repo>/meta/editorial-standard.html.

Структура одной главы

Каждый файл главы — самодостаточный HTML, который можно открыть отдельно. При сборке извлекается содержимое между маркерами CHAPTER-CONTENT:

<!DOCTYPE html> <html lang="ru"> <head> <link rel="stylesheet" href="../styles.css"> <title>Глава 4. Функциональные требования — Системный анализ: карманный справочник</title> </head> <body> <div class="layout"> <!-- TOC-GLOBAL-INCLUDE --> <aside class="toc-global">...</aside> <!-- /TOC-GLOBAL-INCLUDE --> <main> <!-- CHAPTER-CONTENT-START --> <article class="chapter" data-chapter="04"> <header class="chapter-header">...</header> <section id="ch04-use-cases">Тема 1...</section> <section id="ch04-user-stories">Тема 2...</section> </article> <!-- CHAPTER-CONTENT-END --> </main> <!-- TOC-LOCAL-INCLUDE --> <aside class="toc-local">...</aside> <!-- /TOC-LOCAL-INCLUDE --> </div> </body></html>

Если нет Python

На macOS и Linux Python предустановлен. На Windows можно установить с python.org. Если ставить Python нет возможности — сборка выполнится автоматически через GitHub Actions при push в main; локальная сборка нужна только для проверки результата перед коммитом.
